## 2. Candidates, ranked

1. **The idle work search's candidate tree (`Helper_sub_8000` 0x1400f8000,
   `src/game/Component/citizenai_housing_idle.cpp`).** 9.9% of the spread town's sim update (5.5% of it in
   `MemAlloc`, 2.4% in the AVL rebalance `CitizenAI_Reg_helper_e360<WorkCandidateNode>`). Each idle citizen's
   search inserts every job of its scheduler bucket into a fresh AVL keyed (Work +0x24 cost, Work +0x20 tiebreak),
   duplicates dropped, one 0x30-byte sim-heap node per insert, then walks it in order. A sorted flat array with
   the same key, the same duplicate rule and the same visit order would give the same result (GRIDSEARCH /
   PATHDIST's method, a COMPPROF=4 shadow against the AVL). **Check first:** whether anything observes the sim
   heap's allocation sequence (pointer-ordered `Set<ComponentEntity*, AVLCompare>` trees exist: if later
   allocations land at different addresses, their iteration order could change). If it does, this is class B,
   not faithful.
2. **The character move tick (31% of the update).** banished-perf's two-phase parallel movement: AI step in the
   entity loop, then the movement math on workers and the stores in update order on the main thread (their
   stress town 1.28x -> 1.87x with parallel AI). Not exact (later entities see a character's start-of-tick
   position): a class B row. The largest single target; also the most work.
3. **The crowding check (`QueryNearestCharacter`, 4-7%).** The same banished-perf write-up defers the
   MoveTo::vf6 calls to the workers after movement. Rides on item 2.
4. **The shadow pass on the draw side (~23% of the main thread).** The biggest draw item that is ours; for the fps
   at low speed, not the sim.
5. Animation (~10% of the update): banished-perf found poses cannot be skipped exactly (root motion), so only a
   class B route exists; ext.anim_batch already covers the speed-N case.

Dropped by this profile: **the pathfinder.** Its worker is 89% idle in the spread town (the search 10% of its
samples), `RegionGraph::FindPath` 1.0-1.5% of the update. Nothing left to win there.

## 3. Measurement finding: the draw-sort census in every stress run

`DrawSort::g_profOn` is set whenever `BANISHED_STRESS_COMPPROF >= 1` (`stress_harness.cpp:180`), which the
stress harness turns on, so every stress run sorts through `SortFastSwitch<true>`: `CensusInput` hashes every
draw list (`KeyArrayHash`, `ItemArrayHash` x2, 7 qwords per item) to count repeats. That is 10.7% of the main
thread's samples (compact) and 14.8% inclusive; it never runs in play. Stress `frame ms` / fps figures carry it
(the sim ms do not). Worth gating the census to its own COMPPROF level before the next draw-side A/B.
